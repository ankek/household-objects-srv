# tenant_isolation_coverage.txt -- NFR-010's coverage list (T046).
#
# WHAT THIS FILE IS
#
# One line per route the API actually serves, recording whether that route's cross-group isolation
# property is tested. It is the *claim*; `hho routes` is the *fact*. .orchestra/scripts/gate-tenant-
# isolation.sh diffs the two and fails when a registered route has no line here, which is the exact
# defect NFR-010 exists to prevent: an endpoint shipped with no isolation test and nobody noticing.
#
# FORMAT
#
#   <METHOD> <path>  <status>: <detail>
#
# The first two whitespace-separated fields are the route key and must byte-match a line of
# `go -C server run ./cmd/hho routes`. The third field is the status token:
#
#   exempt:      the route authenticates nobody, so there is no tenant to cross. Counted as
#                covered. Every unauthenticated route is listed here EXPLICITLY rather than left
#                out, because an omission and a forgotten route look identical to the gate.
#   covered-by:  a test asserts this route's cross-group behaviour. Name the test (and its
#                subtest), as a string `go test -run` accepts verbatim, so a reader can go and
#                check the claim rather than trusting it.
#
#                Three assertion shapes count, because the API has three shapes of route. For a
#                route that takes a resource id, it is the cross-group 404: authenticated as group
#                B, naming a group-A id, the answer must be 404 and never 403 -- a 403 confirms the
#                id exists, which is the existence oracle FR-008/NFR-010 forbid. For a collection
#                route, which takes no id and correctly answers 200, it is the same property
#                stated over the response: the other group's ids must be absent from the caller's
#                listing. The second is not a weaker claim; it is the only form the first can take
#                where there is no id in the request to be wrong about.
#
#                The third shape applies to the CREATE routes that take NO resource id (POST
#                /invites, POST /auth/device-tokens, T048; POST /items, T051). A create route that
#                DOES name an existing resource -- POST /items/{itemID}/warranty (T052) names the
#                parent item -- is the FIRST shape, not this one: there is an id in the request to
#                be wrong about, so the cross-group 404 applies directly and is the stronger claim.
#
#                The three id-less create routes take neither a resource id nor
#                a collection to probe going in, so neither of the above applies. Their tenant
#                property -- the row a create call produces lands in the CALLER's group -- is
#                enforced structurally: inviteCreateHandler and deviceTokenIssueHandler both pass
#                GroupID: identity.Group, the authenticated scope, never a request field, and
#                itemCreateHandler passes middleware.Scoped's storage.Scope through to
#                items.Create, whose storage.ItemRepository declares no method taking a group
#                identifier at all -- so there is no group id for a caller to even name. P-3's
#                group-bound repositories (T026) and TestUnscopedConstructionDoesNotCompile (T030,
#                server/tests/tenant_isolation/compilefail_test.go) enforce and guard that at
#                compile time. A covered-by: line for a create route cites that structural test
#                as its primary claim, plus a belt-and-braces RUNTIME assertion in
#                TestTenantIsolation (T048): create the resource as group B, and assert the new
#                row is present in B's own listing and absent from A's. This is still one
#                covered-by: line, not a new status token -- see A85 on why a status token that
#                could be satisfied by typing a word would defeat T050's premise.
#
#   cross-tenant-by-design:  the route authenticates SOMEBODY (so exempt: does not apply), but its
#                own spec deliberately gives one authenticated caller every tenant's data, so a
#                cross-group-404 / collection-absence / structural-scope test would be asserting
#                the ABSENCE of the one property the route exists to have. GET /api/v1/backup
#                (T113, FR-132) is, as of T113a, this status's only member: an authenticated
#                owner of ANY group receives a snapshot of EVERY group's data by design (see
#                storage.Storage.VacuumInto's own doc, "a whole-database operation with no tenant
#                of its own," and backup.WriteArchive's signature, which has no group parameter at
#                all to filter by).
#
#                Naming the test is required here exactly as covered-by: requires it, but the test
#                named must assert the INVERSE property, POSITIVELY: that an owner authenticated in
#                one group genuinely DOES receive another group's rows in the response, on purpose.
#                This is what keeps this status from being T050/A85's exact hazard -- a token
#                satisfied by typing a word rather than by evidence. "exempt:" is falsifiable by
#                testing for a 401 (T113's own backup_test.go already does, and did before this
#                status existed); "covered-by:" is falsifiable by testing for isolation; this status
#                is falsifiable the same way, in the opposite direction -- the moment a future
#                change narrows the route to the caller's own tenant (deliberately or by accident),
#                the named test starts failing on exactly that change, converting "this route has
#                no isolation property" from an untested assertion in this file's prose into a
#                claim a reader can run `go test -run` against and watch fail the day it stops
#                being true. A line here that named no test, or named a test that only checked
#                status codes/headers/stream-validity (what T113's own backup_test.go already
#                covers) without ever asserting a SECOND group's row is actually present, would be
#                exactly the un-evidenced word T050/A85 warn against, so the gate crosscheck below
#                treats this status identically to covered-by: (accepted) and nothing lesser is
#                accepted in its place.
#
#                One more requirement, added after T113a shipped without it: the test named must
#                be one gate-tenant-isolation.sh's own isolation-suite step ACTUALLY EXECUTES, not
#                merely one that exists somewhere in the tree. That script runs
#                `go -C server test ... -run 'TestTenantIsolation'` -- an unanchored match against
#                each top-level test's own name -- so a cited test's top-level function must itself
#                match that pattern (carry the TestTenantIsolation prefix, the shape
#                TestTenantIsolationBackupIncludesEveryGroupsData below takes) unless a future
#                change widens the script's own -run pattern AND its neighbouring vacuity guard
#                (the `grep -rqs -- 'func TestTenantIsolation'` existence check immediately above
#                that invocation) to cover the new name too -- widening one without the other
#                reopens the exact hole this paragraph closes, a pattern that matches nothing still
#                exits 0. Citing a test the gate never runs is indistinguishable, in effect, from
#                citing no test at all: the claim can go stale (deleted, renamed, broken) with the
#                gate none the wiser, which is precisely the un-evidenced-word hazard the paragraph
#                above already rules out for every other case.
#
# Any other status (pending:, for instance) is reported by the gate as listed-but-not-covered. That
# is deliberate: writing a line here must not, by itself, satisfy the requirement.
#
# HOW TO REGENERATE THE SKELETON
#
#   go -C server run ./cmd/hho routes --classify
#
# prints "<METHOD> <path>\t<class>\t<isolation>" for every route, where isolation is "exempt" for a
# public route and "required" for a tenant-scoped one. Copy in the new lines, keep the old ones.
#

# What the mutation testing established (every mutation applied to the SQL/Go source, regenerated

#   - Breaking GetGroupVisibility's `id = sqlc.arg(group_id)` predicate ALONE (mutated to
#     `(id = sqlc.arg(group_id) OR 1=1)`) fires immediately and dramatically: with no predicate left
#     to disambiguate, SQLite's QueryRowContext returns household A's row (seeded first, lower
#     rowid) to EVERY caller regardless of which group's id was bound. Household B's GET starts
#     answering with A's settings, and the PUT handler's own internal pre-read (the same query)
#     reads A's version too, so the read-back after a nominally successful write echoes A's STALE
#     state back to B instead of B's real new one; on the second credential-loop iteration this
#     compounds into a spurious 500 (the version the broken pre-read hands the guarded UPDATE no
#     longer matches B's real, already-bumped row). storage/group_visibility_test.go's
#     TestGroupVisibilityGetIsScopedToItsOwnGroup fails on its own under this mutation with exactly
#     this leak, independent of the HTTP-level failure.
#   - Breaking UpdateGroupVisibility's `id = sqlc.arg(group_id)` predicate ALONE is NOT masked by
#     the pre-read the way T054's UpdateItemPurchase was (that item-scoped predicate's masking
#     doesn't reproduce here, because there is no id argument for the pre-read to disagree with the
#     write about) -- it fires immediately as a 500 on both credential-loop iterations, because
#     BOTH households start at version 1 (groups.sql's own default) and a bare `version = ?` with no
#     tenant predicate left matches BOTH rows at once; [groupVisibilityRepository.Update]'s own
#     `rows != 1` invariant guard (expecting exactly one matched row) catches the 2-row result and
#     returns an error INSIDE the write transaction, which [binding.writeTx] then rolls back
#     wholesale -- so group_a_resources_untouched (and storage/group_visibility_test.go's
#     TestGroupVisibilityUpdateDoesNotAffectAnotherGroup) still find household A's row untouched
#     after this SINGLE mutation, not because the predicate is dead but because a second,
#     independent defense (the invariant check plus this package's single-transaction write path)
#     contains the blast radius before it commits. Pairing this mutation with weakening that guard
#     (`rows != 1` relaxed to `rows == 0`, so a 2-row match is accepted as success) is what lands the
#     corruption for real: group_a_resources_untouched then reports household A's row as
#     `{warranty_visible:true version:3}` (bumped twice, once per credential kind) --
#     "carol's own-group toggle bled into alice's group" -- and the SAME storage-layer test fails
#     with the identical shape. This is the double-mutation-proves-load-bearing move T054's
#     UpdateItemPurchase section established, applied to a different mechanism: there, a pre-read
#     masked the predicate; here, an invariant guard plus transactional atomicity does, and both
#     halves have to be broken together to show the predicate is load-bearing rather than redundant
#     with that guard.
#   - Stripping middleware.RequireOwner from PUT (mounting it directly on the general authenticated
#     group like GET) fires immediately: TestOwnerOnlyRoutesRejectMembers's fake-scope case changes

#     registering owner) completes a real 200 write, `{"warranty_visible":true,...,"version":2}`,
#     once the wrap is removed. The scratch test was deleted after confirming the result; it is not
#     part of this task's shipped test suite.
#   - problem.NotFound() -> problem.Forbidden() (T054's third required mutation) does not apply to
#     either route: neither is id-addressed, so [problem.NotFound] renders only on the
#     [storage.ErrNotFound] path each repository's own doc calls unreachable in practice (the bound

# T056 mounts FR-015's item identifications (GET/POST /items/{itemID}/identifications, PUT/DELETE
# /items/{itemID}/identifications/{identificationID}) and covers all four here, in the task that
# mounted them, on the T048/T051-T055 precedent. Coverage now stands at 34 routes: 4 exempt, 30
# covered, 0 pending.
#
# This is the FIRST 0..N child collection under an item -- every prior detail block (warranty,
# sale, purchase, T052-T054) is 1:0..1, addressed by the parent item's id alone. GET/POST here are
# addressed the identical way and are the FORMAT section's first assertion shape (cross-group-404),
# exactly like POST /items/{itemID}/warranty. PUT/DELETE are ALSO the first shape, but each names a
# SECOND id -- the row itself -- which no route above this one has. That second id is the genuinely
# new tenant hazard this task adds: a child id belonging to a DIFFERENT item in the CALLER's OWN
# group, not a different tenant. This suite cannot exercise that hazard at all -- every subtest
# here authenticates as a second, independent GROUP, never as a second item within one group -- so
# it is proven instead at the storage layer, in
# server/internal/storage/item_identifications_test.go's
# TestIdentificationGetRejectsAnotherItemsRowInTheSameGroup,
# TestIdentificationListExcludesOtherItemsRowsInTheSameGroup,
# TestIdentificationUpdateRejectsAnotherItemsRowInTheSameGroup and
# TestIdentificationDeleteRejectsAnotherItemsRowInTheSameGroup. See T056.md's mutation table for the
# full results; the summary:
#   - Breaking GetItemIdentification's group_id predicate ALONE fires directly: Get leaks group A's
#     row to group B on a nil error, and Update's pre-read (which calls GetItemIdentification) leaks
#     the same way, but the actual UPDATE statement (its own group_id predicate intact) then matches
#     0 rows against the pre-read's stale, wrongly-scoped version -- caught by the "matched 0 rows,
#     want 1" invariant guard, surfacing as a 500 rather than a silent cross-tenant write. Both
#     TestIdentificationGetRejectsAnotherGroupsRow and TestIdentificationUpdateRejectsAnotherGroupsRow
#     fail under this single mutation.
#   - Breaking GetItemIdentification's item_id predicate ALONE -- the headline new predicate -- is
#     INVISIBLE to every cross-group test in this file (the whole isolation suite stays green) and
#     fires ONLY on the two same-tenant, cross-item storage tests named above
#     (TestIdentificationGetRejectsAnotherItemsRowInTheSameGroup /
#     ...UpdateRejectsAnotherItemsRowInTheSameGroup), exactly confirming the gap this section states.
#   - Breaking ListItemIdentifications' group_id predicate ALONE does not fire: List's own pre-read
#     (a scoped GetItem, unrelated statement) already answers ErrNotFound for a foreign-group item
#     before the mutated statement is reached -- masked, not dead; disabling that pre-read as well
#     lands a real leak (List returns rows with a nil error to a foreign caller), proving the
#     predicate load-bearing once nothing upstream confirms ownership.
#   - Breaking ListItemIdentifications' item_id predicate ALONE was NOT caught by any test that
#     existed before this task ran mutation testing -- List's pre-read only confirms the ITEM belongs
#     to the caller's group, not which item's rows come back, so a same-tenant, cross-item leak (item
#     A's list showing item A2's rows too) slipped through silently. TestIdentificationListExcludesOtherItemsRowsInTheSameGroup
